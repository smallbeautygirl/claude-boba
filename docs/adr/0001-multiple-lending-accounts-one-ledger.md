# 代跑者可以出借多個 Claude 帳號，但人情債不分來源

一位代跑者可能手上有兩個 Claude 帳號 —— 例如個人 Max，以及公司配給他個人的帳號。
這兩個帳號**的錢不是同一個來源**，但我們決定：**帳本完全不區分是哪個帳號跑的**。
債照記，級距照算，債主是那個人。

代價是 SPEC §4.6 原本「花掉的是你的錢」這個敘事不再精確 —— 公司帳號的額度不是他的錢。
所以那句話改寫成：**他借出去的是自己的額度使用權，以及自己帳號的風險敞口**。
這個改寫同時解釋了為什麼失敗不計債、為什麼級距要粗，而且讓公司帳號不需要任何特例。

## Considered Options

**公司帳號不計債。** 誠實，但會產生很糟的誘因：委託者永遠挑那個免費的，
公司額度變成免費停車場 —— 而額度燒光、帳號被停權時倒楣的是代跑者本人（帳號掛他名下）。

**分開記成不同的東西**（例如公司額度只進排行榜不進帳本）。最誠實，也最複雜。
CLAUDE.md 那張表寫著「一條簡單的規則比一條公平的規則值錢」；這個選項正是拿簡單換公平。

## Consequences

- **對委託者，兩個帳號等於不存在。** 他看到的下拉一列一個**人**，指定也只指定到人。
  額度紅綠燈取那個人底下**最充裕**的帳號 —— 那顆燈的語意從「他的帳號」變成「他的池子」
  （docs/web-spec.md §3）。
- **既然對外不可區分，條件也不分帳號。** 花費上限／可用 model／外網開關屬於**人**
  （出借設定，每人一份）；額度、rate limit、token、併發上限屬於**帳號**（出借帳號，每人 N 個）。
  資料模型上 `Worker` 因此拆成兩張表。
- **`Job` 兩個都記**：`lending_id`（誰的債、用誰的條件）與 `account_id`（實際燒了哪個帳號）。
  `account_id` 不對委託者顯示，它存在的理由是「上個月公司帳號跑了幾個 job」這個問題
  一定會被問到 —— 見下一條。
- **公司帳號要有具名批准者。** 授權一個出借帳號時要填「這是誰的額度／誰批准的」，
  純文字、站台不驗證，只是留痕跡並顯示在管理頁。
  理由是託管模型下 token 存在共用主機（見 SPEC §1 的合規取捨），
  個人帳號被停權是他自己倒楣，公司帳號被停權是公司資產出事、而且會有人問是誰放的。
- **派單在同一位代跑者的帳號之間，挑 utilization 低的那個**（冷啟動或資料過期時退回輪流）。
  這是知情取捨：它讓公司帳號從「溢出用」變成穩定約一半的曝險，
  換到的是兩個帳號都不容易撞 rate limit。**因此管理頁必須看得到「有多少 job 跑在
  標了批准者的帳號上」** —— 否則批准者名字留了痕跡，用量卻沒人看得到，等於只留一半。
