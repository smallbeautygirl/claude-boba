# 許願板允許公開貼圖 —— 知情地弱化 §4.3

許願板（web-spec §12）上的願望與留言**都可以貼圖**，四個分類一律開放，不限
「壞掉了」那一類。圖片對**所有登入者公開**、署名、而且活到牆被拆掉為止。

這一條**弱化了 SPEC §4.3**。那一節的立場是「誠實揭露 + 預設不看」，而這個專案至今
所有對外顯示的東西都是聚合數字（web-spec §7 為此拒絕了動態牆）。這是**第一次**
有使用者上傳的原始內容被放在一個公開頁面上。

換來的是「壞掉了」與「體驗不好」這兩類回饋真的可用 —— 沒有截圖的 UI bug 回報，
往往等於沒有回報，而許願板存在的理由就是試玩期回饋不足。

## Considered Options

**不做，需要截圖時私下跟他要。** 這是被放棄的那條，而它的論證是最強的：
一張 job 詳情頁的截圖會把 prompt、檔名、花費金額一次全帶上一面公開、署名、
永久的牆，而**貼的人不會意識到** —— 他當下的注意力在那個壞掉的按鈕上。

**只給「壞掉了」這一類開放，上傳前顯示警告。** 表面上是折衷，實際上更糟：
那句提示擋不住它要擋的東西（急著回報 bug 的人會按掉），而分類開放與否的不對稱
會讓人改用「我再開一則『壞掉了』」來繞過。**一個有警告的公開上傳正是虛假安全感**，
而這個專案在 §4.3 與 README 的合規論述裡一直拒絕製造虛假安全感。

## Consequences

- **風險承擔者就是貼圖的人自己**，這是它跟另一條弱化（代跑 token 存在共用主機，
  SPEC §1）根本不同的地方。那一條的受益者與風險承擔者是分開的（大家方便、代跑者
  承擔），所以它需要非常重的揭露；這一條不是，所以一句話夠。
- **提示文案放在上傳按鈕旁邊，不放頁面頂端**，語氣正經（web-spec §9 的正經清單
  因此從三項變四項）。頂端說明區的字，人在急著回報 bug 的時候不會讀 ——
  web-spec §10 已經為了同一個理由拒絕過「獨立的新手說明頁」。
- **不收 `svg`。** 只收 `png` / `jpeg` / `webp`。這不是效能限制，是安全限制：
  `svg` 可以帶 script，而這是一面會渲染別人上傳內容的公開頁面。
  單張 5 MB、一則最多 3 張，前端先擋（沿用 web-spec §3 的原則）。
  §3 那組 50 MB 是為 `.jsonl` transcript 訂的，**對截圖沒有意義，不要沿用**。
- **圖片不給公開永久網址。** 存在 `wishes/{user_id}/`，讀取走 hub 一個要登入的端點
  （SPEC §8）。一張帶 prompt 的截圖若有不用登入就打得開的位址，外洩得比這面牆本身
  更遠 —— **圖片的可見範圍必須等於牆的可見範圍**，不能因為它是靜態檔就偷偷放寬。
- **`wishes/` 排除在 30 天 lifecycle 之外**，改成隨牆下架一起刪。理由與陷阱見 SPEC §8。
- **如果決定收回這一條**，要記得已經貼出去的圖不會因為關掉上傳而消失。收回等於刪檔，
  而刪檔會讓舊願望的內文失去意義。這是「難反轉」的具體形狀。
